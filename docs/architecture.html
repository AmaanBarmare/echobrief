Architecture map · 2026-08-20

A meeting goes in as audio.
It comes out as decisions.

EchoBrief is one product spread over four runtimes: a React SPA, 29 Deno edge functions, a Postgres database that doubles as the job scheduler, and one Node function on Vercel that exists purely because ffmpeg does not fit anywhere else. This page draws how they fit together, where the pipeline breaks, and what it takes to get it running end-to-end.

01 — System at a glance

Four runtimes, one meetings table

The browser never talks to Recall, Sarvam or OpenAI. It talks to Supabase, and every provider hop happens inside an edge function holding a service-role key. The single exception is api/split-audio, which lives on Vercel because ffmpeg needs 2 GB and a real binary.

Why Vercel at all

Supabase edge functions cap at ~256 MB and ship no ffmpeg. Chunking a 47-minute MP3 needs both. So one function moved out, reached over HTTPS with a shared bearer secret.

Why the DB schedules jobs

pg_cron + pg_net fire the three recurring jobs. Cheap, but every tick writes rows — which is exactly what drained the Disk IO budget once already.

One ingest, one pipeline

The Chrome extension path is gone. Everything is bot-recorded now, and everything downstream of meetings is ingest-agnostic.

04 — Failure & fallback

Four transcription paths, tried in order

Each rung exists because the one above it failed in production. Read top to bottom as a descent: the further down a meeting falls, the more likely a human has to touch it.

Rung 1 — chunked Sarvam default

Splitter cuts 300 s chunks, one multi-file job, webhook stitches. Handles any length. This is the path that should carry ~100% of traffic.

api/split-audio.ts → _shared/sarvam.ts → sarvam-webhook

Rung 2 — direct Sarvam degraded

Taken only when the splitter is unreachable or SPLIT_AUDIO_URL is unset. Works under ~6 min, silently returns empty above ~7 min. A misconfigured env var lands you here without an error.

_shared/recall-pipeline.ts — legacy submit

Rung 3 — chunk-wise Whisper automatic

Sarvam returned empty, or threw its KeyError: 'timestamps'. The webhook re-calls the splitter in transcribe: "whisper" mode; each chunk is ~1 MB, so Whisper's 25 MB limit never bites. Needs OPENAI_API_KEY in the Vercel env.

api/split-audio.ts?transcribe=whisper

Rung 4 — in-edge Whisper known broken >15 MB

process-meeting with forceWhisper: true. Three copies of the blob in ~256 MB of RAM means WORKER_RESOURCE_LIMIT for anything sizeable. Only reachable for non-chunked audio; recovery below it is a manual script that isn't in the repo.

supabase/functions/process-meeting/index.ts
Sharpest edge in the system

Rungs 1 and 3 both route through Vercel. If SPLIT_AUDIO_URL, SPLIT_AUDIO_SECRET (Supabase) or SPLIT_AUDIO_SECRET, SARVAM_API_KEY, OPENAI_API_KEY (Vercel) drift out of sync, long meetings fail quietly — a completed Sarvam job with an empty transcript, no exception anywhere. Verifying those five values is step one of any "why is nothing working" investigation.

05 — Races and locks

Two webhooks, one row, milliseconds apart

Recall fires audio_mixed.done and bot.done almost simultaneously. Every serious bug in this pipeline's history came from two handlers reading the same row before either had written to it.

The transcribing deadlock

check-recall-status used status = 'transcribing' as an optimistic lock. sarvam-webhook had that same value in its skip list. Two handlers, one string, opposite meanings — permanent stall.

Fix: meetings.sarvam_webhook_triggered_at, claimed with an atomic IS NULL update and released on failure.

The missing column

Every failure path wrote error_message to a column that did not exist. The UPDATEs no-op'd for weeks, so failures were invisible in the UI.

Fix: migration 20260424170000, plus a harness scenario that would have caught it.

The infinite retry

A 23-second silent meeting: Sarvam wrote no output, the webhook threw a 500, and the poller retried every 5 s forever.

Fix: a missing output is a legitimate outcome, not an exception — handle and terminate.

06 — Self-healing layer

The database is also the scheduler — and that costs IO

Three pg_cron jobs call edge functions over HTTP via pg_net. Cheap in money, expensive in write churn: at one tick per minute, net.http_post was 94.4% of all database execution time.

If you ever need finer scheduling

Move it off the database to a free external scheduler (cron-job.org, GitHub Actions) hitting the edge functions directly. Not Vercel Cron — its free tier caps at once per day — and not a paid compute upgrade to paper over write churn.

07 — Data model

meetings is the hub; everything else hangs off it

Every user-scoped table enforces auth.uid() = user_id at the database level, so the SPA's anon key is safe to ship. monitor_events is the one service-role-only table.

10 — Test tiers

Four tiers, and each one has caught a real bug

Run them in order of cost. The bottom two are free and fast; the top two cost real API calls and prod writes.

Tier 0 — unit, <1 s

26 deno tests, fetch mocked, no network. Covers recall-pipeline URL discovery and fallbacks, getAudioMixedStatus defer semantics, chunk-stitch offsets and ordering, Sarvam output discovery.

npm run test:unit

Run on: any shared-logic change.

Tier 1 — integration, ~90 s

11 scenarios against real deployed functions and the real database, creating and deleting [harness]-prefixed meetings. Already caught two prod bugs: the missing error_message column and the transcribing deadlock.

python3 scripts/pipeline-test/harness.py

Run on: any edge function or migration, before deploying.

Tier 2 — live provider, ~3 min extra

Real fixture audio through the deployed splitter, a real chunked Sarvam job, real stitched completion. Doubles as a contract check against Sarvam's API.

python3 scripts/pipeline-test/harness.py --live

Run on: risky pipeline deploys.

Output quality — 8 evals

4 deterministic + 4 LLM-judge graders over a static dataset: schema, English output, stitch integrity, speaker attribution, action-item recall and precision, summary faithfulness, decision accuracy. One case must FAIL — that's the judge calibration.

python3 scripts/evals/run_evals.py

Run on: anything touching transcription or insights.

Tier 3 — the manual drill

No harness substitutes for it after bot-flow changes: open a Meet, dispatch a bot from the dashboard, admit it, talk for a few minutes, confirm the meeting completes with real participant names rather than SPEAKER_00.

11 — Get it working

The shortest path from cold repo to a completed meeting

Config drift, not code, is what usually breaks this system. Work down the list; each step fails loudly if the one before it didn't take.

  1. Reconcile secrets in three places. Frontend .env (2 vars) · Supabase Edge Function secrets (Sarvam, OpenAI, Recall, Resend, Google, SPLIT_AUDIO_URL, SPLIT_AUDIO_SECRET) · Vercel env (SARVAM_API_KEY, OPENAI_API_KEY, SPLIT_AUDIO_SECRET). The two SPLIT_AUDIO_SECRET values must be byte-identical.
  2. Confirm the splitter answers. An unauthenticated POST should return 401 and a bad body 400 — the harness probes exactly this. A 404 here means every long meeting silently degrades to rung 2 and comes back empty.
  3. Run the free tiers. npm run test:unit, then npm run build. Both should be green before anything is deployed.
  4. Run the integration harness. 11/11, or read the failure — it names the scenario and the meeting id it left behind. Expect a [ECHOBRIEF HARNESS TEST] email; real delivery is part of the test.
  5. Check the cron jobs are actually scheduled. Three rows in cron.job: auto-join every 5 min, monitor every 15 min, prune daily at 03:15 UTC. Absent crons mean nothing self-heals and stuck meetings sit forever.
  6. Do the manual bot drill. One real Meet, a few minutes of speech, and check the result has real names on the segments. This is the only test that exercises Recall's transcript path end-to-end.
  7. Then run the evals before touching prompts or transcription: python3 scripts/evals/run_evals.py. Exit code gates the deploy.

Known gaps, worth deciding on before building anything new

In-edge Whisper still OOMs

Rung 4 is broken above ~15 MB and has no automatic recovery for non-chunked audio. The documented manual fallback (/tmp/recover_meeting.py) is not in the repo and does not currently exist on this machine.

Options: stream the upload instead of buffering three copies, or route every Whisper attempt through the splitter and delete the in-edge path.

Types compile-clean only by accident

npm run build is green because Vite uses SWC and skips type checking. tsc --noEmit still reports pre-existing errors — a const-widening mismatch in src/lib/theme.ts and lucide icon prop types in Auth.tsx.

Options: fix the two patterns and add tsc --noEmit to CI, or accept it and stop pretending the build type-checks.

Silent degradation on config drift

A missing SPLIT_AUDIO_URL produces no error — just short meetings that work and long ones that come back empty. The failure is invisible until a user complains.

Options: a startup assertion in recall-pipeline, or a monitor signature for "fell back to direct submit".

Peripheral integrations carry weight

WhatsApp (Gupshup), Notion sync and digest reports are wired but off the critical path. They add functions, secrets and surface area to keep alive.

Options: confirm each is wanted for launch, or park them the way the Chrome extension and Slack were removed.

Two rules the repo will enforce on you

95% confidence: don't change code you aren't 95% sure about — ask instead. Test before deploying: unit harness on shared logic, pipeline harness before any edge function or migration, evals before anything touching transcription or insights. And when the monitor emails a new error, update errors.md and known-patterns.ts together or they drift.
